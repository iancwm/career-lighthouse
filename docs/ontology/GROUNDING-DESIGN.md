## Problem Statement

The ontology design (`docs/ontology/ONTOLOGY-DESIGN.md`) specifies a well-structured
ingestion pipeline: Stages 1-5 extract Claims from source documents, back them with
Evidence excerpts, and route them through the existing IntentCard review UI. But the
design has no Stage 6. There is no specification for how approved Claims reach the LLM
during student chat.

The current chat pipeline — Qdrant chunk retrieval → LLM context window — does not
distinguish between "what the KB knows" and "what Claude 3.5 Sonnet was trained on."
When the KB doesn't cover a question, the LLM fills the gap from training data. For
general career advice, that's acceptable. For SG-specific employer processes (EP
sponsorship conditions, Goldman's HireVue → SuperDay sequence, DBS intake calendar),
training data is systematically less reliable than counsellor notes and alumni interviews.
Counsellors who put that information into the KB expect it to be the answer source — not
a supplement to whatever the model already "knows."

## Demand Evidence

Pre-production. The failure mode is anticipated structurally, not empirically observed:
LLMs fill knowledge gaps by default. For a career counselling tool where counsellors stake
their professional reputation on the advice their tool gives students, "probably right"
is not enough. The demand is implicit in the design decision to build an ontology at all —
if grounded answers weren't the goal, structured Claims would add complexity with no
payoff.

The narrowest evidence of the problem: the ontology design mentions scope fields
(geography, programme_id, academic_year) specifically to prevent overgeneralization —
"a Goldman SG alumni interview should not become a Goldman global employer-wide claim."
That constraint exists in the ingestion design but nowhere in the generation design.

## Status Quo

Before the Milestone 2 wiring, the chat pipeline (`api/routers/chat_router.py`) was:
1. `active_career_type` detection (keyword match or LLM)
2. Qdrant vector search over raw document chunks
3. Context block assembled: employer notes + track info + KB chunks
4. LLM generates answer

There was no signal to the LLM about what was KB-grounded vs. training-data-derived, no
constraint on gap-filling, and no scope filtering at retrieval time for geography or
programme. Approved Claims now live in `knowledge/claims/`; the Milestone 2 chat path reads
them only when `ontology.grounding_enabled` is enabled. With the flag off, the existing
chat path is unchanged.

## Target User & Narrowest Wedge

**User:** Counsellors at SMU who use the admin workspace to upload employer notes and
alumni interviews, then trust the student-facing chat to reflect what they put in.

**Narrowest wedge:** One employer (Goldman Sachs Singapore), one claim type
(`recruitment_stage`), one query ("What are Goldman's interview stages in Singapore?").
If a student gets an answer traceable to a specific `RecruitmentStagePayload` claim
with `scope.geography="SG"`, the pattern generalizes to every employer and claim type
that Milestone 1 can extract.

## Constraints

- Milestone 1 must ship first: `ClaimStore.list_claims_for_entity()`,
  `EntityStore`, `EvidenceStore` are prerequisites; that dependency is now
  satisfied.
- No new Qdrant collection in this milestone (deferred to Approach B / Milestone 3).
- Additive to existing chat pipeline. Entity resolution failure must fall through to
  current behavior — the change is invisible for queries where no entity is resolved.
- Feature-flagged: `ontology.grounding_enabled: false` in `api/cfg/kb.yaml`,
  same pattern as `ontology.extraction_enabled`. Both current gates are global;
  staging operators must restrict enabled use to the chosen pilot employer.

## Premises

1. The Claims/Evidence/Source model is the right foundation — extending it, not replacing it.
2. The gap is specifically the retrieval/generation side: approved Claims need to reach
   the LLM during student chat.
3. Milestone 1 (models, stores, extraction pipeline, review UI) is the right first
   implementation step. This is Milestone 2.
4. "More grounded" means three concrete things: claim-constrained generation (say
   "I don't have specific information" when no claim exists), scope-aware retrieval
   (SG claims don't become global advice), and citation traceability (counsellors can
   see which source backed the answer).

## Approaches Considered

### Approach A: Minimal — Prompt injection of pre-fetched claims (chosen)

Resolve the employer entity from the student query, retrieve all approved Claims for
that entity from `ClaimStore`, inject as a `VERIFIED CLAIMS` block into the LLM
prompt. Add a constraint: "Only assert facts from VERIFIED CLAIMS; for anything else,
say 'I don't have specific information.'" Scope filtering is deterministic (filter by
`scope.geography`, `valid_until`), not semantic.

Effort: S (1-2 weeks after M1 ships). Risk: Low. No new infrastructure.

Key unknown: entity detection from a natural-language query. Multi-entity queries ("Compare
Goldman and Morgan Stanley") are out of scope for M2 — resolve the first confident entity
only, or return `None` if ambiguous. For single-entity queries, a keyword match against
`EntityStore.list_entities()` is the starting point.

### Approach B: Complete — Evidence-indexed Qdrant collection + citation pipeline

Add a second Qdrant collection (`career_lighthouse_evidence`). When a Claim is approved,
index its Evidence excerpts with `claim_id`, `entity_id`, and scope metadata. Replace
chunk retrieval with evidence retrieval for entity-resolvable queries. LLM receives
structured context blocks with confidence and `authority_tier`. Response includes
`claim_id`s → frontend shows citations.

Effort: XL (6-8 weeks after M1 ships). Risk: High. Right architecture for the long term,
wrong first step when the claim corpus is empty.

### Approach C: Hybrid — Claim summary chunks in existing Qdrant

When a Claim is approved, generate a structured "claim chunk" and upsert it into the
existing Qdrant collection with a `chunk_type: "claim"` metadata tag. Chat retrieval
remains vector-search-first, but claim chunks are preferentially ranked.

Effort: M (2-3 weeks). Risk: Medium. Reuses existing Qdrant infrastructure but mixes
ingestion and retrieval concerns in one collection in a way that's hard to unpick.
Retrieval quality still depends on semantic similarity rather than deterministic entity
lookup.

## Recommended Approach

**Approach A: Minimal claim injection**

**New module: `api/services/claim_context.py`**

```python
class ClaimContext(BaseModel):
    entity_id: str | None = None
    entity_name: str | None = None
    claims: list[Claim] = []
    coverage_confidence: Literal["high", "medium", "low", "none"] = "none"
```

**Step 1: Entity resolution (called from `chat_router.py`, not from inside `llm.py`)**

`ClaimContextService.resolve_entity(employer_slug: str | None, query: str) -> str | None`

`ClaimContextService` is invoked from `chat_router.py` alongside the existing
`employer_store.to_context_block()` call (line 229). The employer slug is exposed via a
new `employer_store.get_matched_slugs(active_career_type, query_text) -> list[str]` method
(additive, does not change `to_context_block()`'s return type — that function returns a
formatted string, not slug strings). `chat_router.py` calls `get_matched_slugs()` alongside
`to_context_block()` and passes `matched_slugs[0]` if exactly 1 slug matches, or `None`
if 0 or >1 slugs match (ambiguous — multi-entity queries fall through to current behavior),
as the `employer_slug` argument to `ClaimContextService.resolve_entity()`.

**`get_matched_slugs()` strict matching:** Uses a private `_match_by_name_or_slug()`
helper that checks only `employer_name` and `slug` fields. Does NOT use the broadened
notes/application_process field expansion from `_employer_matches_query()` (which is
intentionally broader for context injection but too loose for entity resolution — a student
asking about "NGO volunteer work" should not trigger WWF claim injection because WWF's
notes mention "NGO"). `active_career_type` is accepted for API symmetry but does not
filter matching results — name/slug matching runs across ALL employers regardless of
career type (a first-session student with no career type who names Goldman explicitly
still gets claim injection).

**M1 naming convention contract (implemented):**
Organization entities created for known employers use
`entity_id = f"organization-{employer_slug}"`, where `employer_slug` matches
the `knowledge/employers/` filename convention (e.g.,
`goldman_sachs`). `EntityStore.create_entity()` accepts an explicit
ID, and `ensure_organization_entity_for_employer()` owns this convention. The
generic store method does not reject every other valid entity ID.

**M1 API contract (implemented):**
`ClaimStore` must expose: `list_claims_for_entity(entity_id: str, review_status: str | None, lifecycle: str | None) -> list[Claim]`

- **Fast path** (employer slug from `get_matched_slugs()`): derive entity_id directly
  as `f"organization-{employer_slug}"`. No `EntityStore` lookup needed. Handles the
  majority of queries where employer context is present. Measure fast-path hit rate at
  pilot time; if >80%, the keyword normalization fallback can be deferred to a later milestone.

- **Keyword normalization fallback** (0 slugs matched — employer not explicitly named in
  query): iterate `EntityStore.list_entities(entity_type="organization") -> list[Entity]`
  where each `Entity` has at minimum `{entity_id: str, canonical_name: str, aliases: list[str]}`.
  Tokenize each entity's `canonical_name` and `aliases` using the same `_normalized_terms()`
  pattern from `employer_store.py`. Match against tokenized query terms. If exactly one entity
  matches, resolve to that `entity_id`; if zero or multiple match, return `None`. This is
  keyword matching, NOT ML-based NER. M1 exposes this interface and M2 wires it
  into the flag-gated chat path.
  Validate normalization conventions match `EmployerEntityStore` before reusing
  `_normalise_name_key()` — a thin adapter may be needed.

- If zero or multiple confident matches: return `None` (ambiguity → fall through to
  current behavior, no injection).

**Step 2: Claim retrieval**

`ClaimContextService.get_claims(entity_id: str, scope_geography: str | None) -> list[Claim]`

`scope_geography` defaults to the `ontology.grounding_default_geography` config key in `kb.yaml`
(pilot value: `"SG"`). Per-query geographic detection is deferred to a later milestone.

```python
claims = claim_store.list_claims_for_entity(
    entity_id=entity_id,
    review_status="approved",
    lifecycle="active",
)
# Scope filter: prefer geography-specific claims; fall back to unscoped claims.
# Stale claims (valid_until < today) pass through to scoring — they affect the
# coverage_confidence tier rather than being silently dropped.
claims = [
    c for c in claims
    if c.scope.geography in (scope_geography, None)
    and c.assertion_status not in ("contradicted", "superseded")
]
```

**Step 3: Coverage confidence**

Stale claims (`valid_until < today`) are included in the scoring step (not pre-filtered)
so they can downgrade the tier rather than silently disappear. Tiers are internal metrics
and pilot-evaluation signals — the prompt injection behavior is the same regardless of
tier (inject the VERIFIED CLAIMS block if non-`"none"`). The tier governs supplementary
caveat language, not whether the block appears.

```
"high":   >= 3 claims, all with valid_time.valid_until >= today or valid_time.valid_until=None,
          AND mean c.confidence.extraction >= 0.7 across included claims
"medium": 1-2 claims total, OR mean c.confidence.extraction < 0.7 across all claims,
          OR any stale claim present alongside non-stale ones
"low":    all claims are stale (valid_time.valid_until < today) — inject with caveat:
          "Note: this information is from [year] and may be outdated."
          [year] = max(c.valid_time.valid_until.year for c in claims
                       if c.valid_time.valid_until is not None),
          falling back to "outdated" if all valid_time.valid_until fields are None.
"none":   0 claims → no injection, existing behavior unchanged
```

**Step 4: Prompt injection**

Add `claim_context: ClaimContext | None = None` to `chat_with_context()`'s signature
(`api/services/llm.py:770`). `ClaimContextService.get_claim_context()` is invoked from
`chat_router.py` alongside the existing `employer_store.to_context_block()` call, and the
result is passed in as this parameter. Do not invoke `ClaimContextService` from inside
`llm.py` — that would couple service layers.

When `claim_context` is not None and `coverage_confidence != "none"`:
- Insert the VERIFIED CLAIMS block at position 0 in `context_sections` (line 858), before
  career profile and employer blocks, so it is the first thing the LLM reads.
- Apply `_trim_to_budget(claim_block, max_context_chars // 6)` as a character cap before
  inserting. At default `max_context_chars=12,000`, this gives 2,000 chars to the claim
  block (~10 claims at 200 chars each). The stricter cap (// 6, not // 3) is intentional:
  `_join_budgeted_sections` is greedy first-fit over `[resume, context, history]`. After a
  5,000-char resume, the full `context_section` gets ~7,000 chars. A 2,000-char claim block
  leaves ~5,000 chars for career profile + employer context + KB chunks. The // 3 cap would
  leave only ~3,000 — crowding out half the KB chunk budget.
  `ontology.max_injected_claims: 10` caps the claim count before budgeting.
- Claims are injected in `ClaimStore` file-system iteration order, NOT query-relevance order.
  At pilot scale (<10 claims per employer) all claims fit within the 2,000-char budget so
  ordering has minimal impact. Relevance-ranked ordering (sort by `claim_type` affinity to
  query intent) is deferred to Milestone 3 (tracked in TODOS.md).
- Pass each claim's display text through `sanitize_for_prompt()` (already imported at
  `llm.py:78`) before concatenating into the block.

```
VERIFIED CLAIMS (from Knowledge Base):
These are verified facts extracted from counsellor notes and employer documents.
Trust these over your general training knowledge. Cite the claim type when you
use one.

• [recruitment_stage] Goldman Sachs Singapore — HireVue video interview (Stage 2,
  modality: video). Evidence: "candidates complete a 15-minute HireVue" (source:
  counsellor_note, authority: internal_counsellor)

• [application_window] Goldman Sachs Singapore — Summer Analyst closes September.
  Evidence: "September deadline for summer analyst applications" (source:
  counsellor_note, authority: internal_counsellor)

If a student asks about something NOT covered by a VERIFIED CLAIM above, respond
with: "I don't have specific information about that in my knowledge base. Based on
general knowledge..." — and clearly signal it's not KB-grounded.
```

**Error rescue (required in ClaimContextService.get_claim_context()):**
Wrap the full method body in `try/except Exception as e: logger.warning("ClaimContext failed, falling through", exc_info=True); return ClaimContext(coverage_confidence="none")`. This ensures any store failure (malformed YAML, missing directory, Pydantic validation error on a claim) falls through to existing chat behavior rather than killing the chat response. Named exceptions (FileNotFoundError, yaml.YAMLError, ValidationError) may be caught individually inside for richer log context, but the outer catch is the mandatory safety net.

**Langfuse grounding metrics implemented in `chat_router.py` → `llm.chat_with_context()`:**
The current trace metadata includes these deterministic signals alongside
`kb_chunks_retrieved` / `kb_chunks_sent`:
- `grounding_entity_resolved: bool` — whether a claim-context entity was resolved
- `grounding_claims_injected_count: int` — number of claims in the block (0 if not injected)
- `grounding_coverage_confidence: str` — `"high"` / `"medium"` / `"low"` / `"none"`
- `grounding_employer_slug: str | None` — the unambiguous employer slug used for fast-path resolution

The earlier design proposed `grounding_entity_resolution_path` and a
`grounding_citation_present` trace field. They are not emitted in Milestone 2.
Pilot evaluation can derive citation presence from the response, but adding
either field requires a separate implementation decision.

**Feature flag test (implemented):**
`test_chat_router.py` patches `grounding_enabled: false`, asserts
`ClaimContextService` is never instantiated, and verifies
`chat_with_context()` receives `claim_context=None`.

**Coverage-confidence "low" tier test (implemented):**
`test_claim_context.py` covers two stale claims, the `coverage_confidence="low"`
path, and the year-bearing staleness caveat. This validates the D1 field path
fix and the staleness text.

**Error rescue tests (implemented):**
`test_claim_context.py` covers both `yaml.YAMLError` and `FileNotFoundError`,
asserting `coverage_confidence="none"` with no exception propagated.

**Eval test (implemented, gated):**
`api/tests/test_grounding_eval.py` uses 3 approved Goldman SG
`recruitment_stage` claims and the gold query "What are Goldman's interview
stages in Singapore?". It is registered in `EVALUATION-PLAN.md` and gated by
`pytest.mark.eval` plus the Anthropic API-key check, so it does not run in the
standard suite.

**Lazy import (required wiring note):**
In `chat_router.py`, import `ClaimContextService` lazily inside the `if grounding_enabled` block (not at module top). Python module-level imports fail at server startup if `claim_context.py` or its M1 dependencies don't exist yet. Lazy import ensures the API starts safely even if M1 is partially complete; any failure is caught by the broad try/except.

**Tiers are initial guesses — tune from pilot data:**
The thresholds (>=3 claims = "high", mean_confidence >= 0.7) are initial estimates with no empirical basis. The pilot evaluation against `EVALUATION-PLAN.md` gold queries is explicitly the calibration step. Do not promote these thresholds to permanent product semantics without measuring against gold queries.

## Open Questions

1. **Entity detection coverage** — Closed for the shipped implementation. The fast path
   uses `EmployerEntityStore.get_matched_slugs()` and derives the stable entity ID from
   one unambiguous slug. The keyword normalization fallback is only needed when no
   employer slug matches. Measure fast-path hit rate at pilot time; if >80%, the fallback
   can remain a low-priority maintenance path.

2. **Context length budget**: how many approved claims can be injected before hitting
   the token budget alongside existing Qdrant chunks? A max-claims-per-query config
   param (`ontology.max_injected_claims: 10`) should gate this. Need to measure at
   pilot time.

3. **All-stale-claims fallback** — Closed. If all claims are stale, inject at
   `coverage_confidence="low"` with a staleness caveat (see Step 3). Falling through to
   `"none"` would cause the LLM to gap-fill with training data, which is worse than
   showing stale but traceable KB data with an explicit date warning.

4. **`SupportType = "contradicts"` in injected evidence**: Closed decision. Claims with
   `assertion_status in ("contradicted", "superseded")` are excluded from injection
   (handled in Step 2's filter). They are never silently dropped — they remain in
   `knowledge/claims/` with their lifecycle state intact and are available to any future
   counsellor-facing data quality surface. This is a read-path exclusion, not a deletion.

## Success Criteria

1. **Pilot acceptance criterion:** once three approved Goldman SG claims are seeded and
   the flag is enabled in staging, a student asking "What are Goldman's interview stages
   in Singapore?" should get an answer containing at least one "per our knowledge base"
   attribution, traceable to a specific `RecruitmentStagePayload` claim in
   `knowledge/claims/`. Citation compliance is LLM-discretionary in M2 (the prompt
   instructs but does not enforce). Pilot evaluation may derive a
   `grounding_citation_present` boolean by scanning responses for the phrase "knowledge
   base"; this is not currently a trace field.
2. A question with no matching approved claims produces an answer that explicitly signals
   the source is general knowledge, not the KB.
3. Existing chat behavior (Qdrant chunk retrieval, track resolution, employer context)
   is unchanged for queries where entity resolution returns `None`.
4. Unit test: `ClaimContextService.get_claim_context("Goldman SG interview process",
   "finance")` returns `coverage_confidence="high"` given a fixture with 3 approved
   Goldman SG recruitment-stage claims.
5. No regression in `pytest api/tests/` from existing chat test suites.
